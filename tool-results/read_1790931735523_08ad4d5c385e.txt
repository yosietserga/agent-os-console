    44→## 1. Reglas Cardinales de Prevención e Invariantes de Calidad
    45→
    46→### 🔴 Regla P1: Verificación Tras Edición (Read-After-Edit Obligatorio)
    47→**NUNCA asumas que una modificación se aplicó correctamente.**
    48→Tras realizar cualquier edición (mediante herramienta, script o parche), el agente
    49→DEBE leer nuevamente la sección modificada del archivo (`git diff` o lectura directa)
    50→para verificar que el nuevo contenido está presente y no ocurrió un no-op.
    51→
    52→### 🔴 Regla P2: Honestidad Absoluta en Puertas de Validación (Gate Honesty)
    53→**ESTÁ ESTRICTAMENTE PROHIBIDO declarar "PASS" sin haber ejecutado el comando real
    54→en esta sesión.**
    55→Si un comando de prueba o compilación no fue invocado, el reporte DEBE declarar
    56→explícitamente `NOT RUN`. Toda afirmación de éxito debe incluir:
    57→(1) el comando exacto ejecutado,
    58→(2) el código de salida ($0$), y
    59→(3) un fragmento representativo del stdout.
    60→
    61→### 🔴 Regla P3: Verificación en Código de Producción (Closes-Finding Guard)
    62→**NUNCA declares resuelto un hallazgo ("Closes Finding X") si la solución solo
    63→reside en un mock o suite de test.**
    64→El archivo de producción debe contener la corrección sustantiva y el test debe
    65→validar el comportamiento real contra la implementación de producción.
    66→
    67→### 🔴 Regla P4: Sincronización Atómica de Código, Contratos y Documentación
    68→Todo cambio en el código debe comprometerse en el mismo turno junto con:
    69→- sus especificaciones de API (OpenAPI, Protobuf, GraphQL SDL),
    70→- la documentación de soporte,
    71→- y la actualización de la memoria empírica
    72→  (`docs/memory/anti-patterns.md` o `docs/memory/wins-ledger.md`).
    73→
    74→### 🔴 Regla P5: Integridad Visual y Estilo Modo Claro Apple
    75→- **Paleta Inmutable:**
    76→  - Fondo Principal: `#ffffff` (Blanco puro).
    77→  - Superficies y Secciones: `#f5f5f7` (Gris titanio claro).
    78→  - Bordes y Separadores: `#e5e5ea` y `#d2d2d7` (Líneas finas de 1px).
    79→  - Texto Titular: `#1d1d1f` (Gris carbón profundo).
    80→  - Texto Secundario: `#86868b` (Gris neutro).
    81→  - Botones y Acentos: `#1d1d1f` (Negro sobrio) o `#0071e3` (Azul interacción).
    82→- **Prohibiciones Visuales:** Cero fondos marrón/mostaza (`#b48a44`).
    83→  Cero Dark Mode absoluto (`#070709`) como tema base del portal principal.
    84→  Cero uso de `!important` para secuestrar la cascada de estilos.
    85→
    86→### 🔴 Regla P6: Estructura Canónica de Layout en 7 Posiciones
    87→Toda interfaz o pantalla debe resolverse mediante las 7 posiciones canónicas del
    88→motor de layout:
    89→`header`, `featuredContent`, `column_left`, `main`, `column_right`,
    90→`featuredFooter`, `footer`.
    91→Queda prohibida la creación de archivos HTML/PHP monolíticos estáticos que ignoren
    92→el motor de resolución dual y dupliquen estructuras base.
    93→
    94→### 🔴 Regla P7: Política "Zero-Placeholder" y "Zero-Emoji"
    95→- Todos los datos comerciales, marcas y medios deben provenir de la configuración
    96→  de la tienda o base de datos. Prohibidos correos de ejemplo o teléfonos
    97→  ficticios (`+1 800 555-0199`).
    98→- Cero emojis en interfaces, botones, títulos o insignias corporativas. Utilizar
    99→  exclusivamente iconos vectoriales SVG o clases iconográficas limpias.
   100→
   101→### 🔴 Regla P8: Aislamiento LLM-Agnóstico (Sin Vendor Lock-in)
   102→**Ningún controlador de negocio puede importar directamente un SDK de proveedor
   103→LLM** (`openai`, `@anthropic-ai/sdk`, `@google/generative-ai`, etc.).
   104→Toda inferencia DEBE pasar por el Control Plane L2 (`packages/l2-client` o su
   105→equivalente polyglot), que enruta a través de un envelope canónico y aplica
   106→circuit breakers, fallbacks y ledger de costos.
   107→Esto garantiza que el código de negocio funcione sin modificación con cualquier
   108→proveedor o modelo local.
   109→
   110→### 🔴 Regla P9: Memoria Append-Only (Inmutabilidad Histórica)
   111→Los archivos `docs/memory/anti-patterns.md`, `docs/memory/wins-ledger.md` y
   112→`docs/memory/worklog.md` son **append-only**.
   113→- Solo se permiten operaciones de anexado (`>>`).
   114→- Está prohibido borrar, reescribir o reordenar entradas existentes.
   115→- Las correcciones se hacen agregando una nueva entrada con referencia
   116→  `[CORRIGE-AP-XXX]` o `[CORRIGE-WIN-XXX]`.
   117→
   118→### 🔴 Regla P10: Declaración de Entornos Dev/Deploy
   119→**El agente DEBE conocer el split de entornos antes de tocar scripts o paths.**
   120→- `.env` define obligatoriamente `DEV_OS` (ej. `windows`) y `DEPLOY_OS` (ej. `ubuntu`).
   121→- Los scripts `*.sh` asumen bash en el entorno de deploy; en Windows-dev requieren WSL o Git Bash.
   122→- `.gitattributes` fuerza `eol=lf` para que los saltos de línea sean consistentes entre Windows↔Ubuntu.
   123→- Las rutas de archivos en código de producción DEBEN usar `path.join()` (Node) o equivalente polyglot; jamás barras hardcodeadas `\` o `/`.
   124→- Los comandos `bun run` / `pnpm run` / `npm run` son válidos en ambos entornos; los scripts `*.sh` son para deploy Ubuntu.
   125→
   126→### 🔴 Regla P11: Onboarding Tour Obligatorio en Vistas Complejas
   127→**Toda vista que cumpla al menos UNO de estos criterios DEBE montar un
   128→`OnboardingTour` canónico** (ver `docs/widgets/onboarding-tour.md`):
   129→1. Tiene >3 secciones interactivas (formulario + tabla + gráfico + sidebar).
   130→2. Es un lienzo de composición (composer, drag-and-drop, visual editor).
   131→3. Tiene >3 métricas analíticas en un solo viewport.
   132→4. Es ruta crítica de onboarding (/, /dashboard, /signup-success).
   133→
   134→**Antipatrón relacionado:** AP-015 "Pantalla UI Compleja Huérfana de Onboarding".
   135→**Verificación:** `persona check <route>` falla para `apprentice` + `demo-master`
   136→si la vista cumple criterios y no monta tour. **Esta regla erradica la necesidad
   137→de re-solicitar Joyrides en cada nueva interfaz.**
   138→
   139→### 🔴 Regla P12: Anti-Prompt-Injection (Defensa en 7 Capas)
   140→**TODO input de usuario y contenido externo ingerido por el agente DEBE pasar
   141→por las 7 capas del protocolo anti-prompt-injection** antes de llegar al LLM
   142→(ver `docs/security/anti-prompt-injection-protocol.md`):
   143→1. Structured prompts con delimitadores canónicos (`<system>`, `<user_input>`)
   144→2. Input validation + sanitization (decode-then-validate, typoglycemia norm)
   145→3. System prompt isolation (sandwich: instrucciones antes Y después del input)
   146→4. Output monitoring + validation (schema + exfiltration detection)
   147→5. Human-in-the-Loop (HITL) para acciones destructivas o hacia externo
   148→6. Least privilege para tools y APIs (sandbox, network allowlist, DB readonly)
   149→7. Comprehensive monitoring + audit (log inmutable en l2_cost_token_ledger)
   150→
   151→**Origen:** Investigación `investiga "prompt injection defenses 2026"` (epoch
   152→1790930597). OWASP LLM Top 10 2026 LLM01 (vulnerabilidad #1 por 2ª edición).
   153→**Verificación:** skill `prompt-injection-scanner` escanea todo input externo.
   154→**Antipatrones relacionados:** AP-022 (sin delimitadores), AP-023 (sin sanitization),
   155→AP-024 (tools excesivos), AP-025 (sin audit log).
   156→
   157→### 🔴 Regla P13: Auto-Crítica Obligatoria (Anti Complacencia)
   158→**TODO artefacto producido por el agente (código, reporte, doc, prompt) DEBE
   159→pasar auto-crítica antes de publicarse.** Mínimo Modo A (self-revision: 3
   160→debilidades reales); Modo D (adversario: 2 vectores de ataque) si toca
   161→seguridad, input externo, o tools (ver `docs/security/auto-critica-protocol.md`).
   162→
   163→- **Tabla AGREE/DISAGREE obligatoria** en todo reporte (al menos 1 DISAGREE
   164→  si exploró algo nuevo; cero DISAGREEs es sospechoso de sesgo confirmatorio).
   165→- **Análisis crítico contrario**: "¿hay mejores formas? ¿newer ways 2026?".
   166→- **Verificación:** comando `critica <file>` genera el reporte.
   167→- **Antipatrón relacionado:** AP-026 Auto-crítica omitida.
   168→- **Origen:** Anthropic Constitutional AI + AgentAuditor (arXiv Feb 2026).
   169→
   170→### 🔴 Regla P14: Headless Browser Verification (No curl/fetch Aislado)
   171→**Verificar que "el server funciona" NO es lo mismo que HTTP 200.** Un HTTP 200
   172→con HTML vacío, errores de consola, CSS roto, o JS no ejecutado es un **éxito
   173→falso**. Toda verificación de rutas que sirven HTML DEBE usar browser headless
   174→(MCP `browser-devtools`) en vez de curl/fetch aislado.
   175→
   176→- **Verificación completa** (10 puntos): navigate + console errors + network
   177→  failures + screenshot + WCAG audit + 7-pos layout + sticky footer + paleta
   178→  Apple + OnboardingTour + CTA Glowing.
   179→- **curl/fetch aislado SOLO válido para**: healthcheck endpoints (`/health`,
   180→  `/ping`) y smoke tests de API sin UI.
   181→- **Verificación:** `ui test <route>` + `expected-check <topic>` usan browser
   182→  headless automáticamente.
   183→- **Antipatrón relacionado:** AP-027 Verificación por curl/fetch aislado de HTML.
   184→- **Origen:** Directriz del operador: "los LLM verifican por curl pero nunca
   185→  por browser headless; un request puede devolver 200 pero realmente no se
   186→  obtuvo el resultado esperado".
   187→
   188→### 🔴 Regla P15: Expected-First Workflow (Generar Expectativas Antes)
   189→**ANTES de implementar cualquier feature, el agente DEBE generar un documento
   190→de expectativas** en `docs/expected/<epoch>-<topic>.md` con:
   191→1. Expectativa visual (wireframe ASCII con 7 posiciones canónicas P6).
   192→2. Expectativa documental (secciones, datos, estados loading/empty/error/success).
   193→3. Expectativa de comportamiento (clicks, hover, keyboard nav).
   194→4. Expectativa de rendimiento (FCP, TTI, P95).
   195→5. Expectativa de accesibilidad (WCAG target, ARIA, focus).
   196→6. Criterios de aceptación verificables (8-15 CAs, cada uno PASS/FAIL/BETTER/WORSE).
   197→
   198→**DESPUÉS de implementar**, ejecutar `expected-check <topic>` que compara el
   199→resultado real (vía browser headless, P14) contra las expectativas, generando
   200→veredicto MATCH / BETTER / WORSE / FAIL.
   201→
   202→- **Skill `expected-spec-generator`** genera el template de expectativas.
   203→- **Comando `expected-check`** (16º canónico) ejecuta la comparación.
   204→- **Antipatrón relacionado:** AP-028 Generación sin expectativas previas.
   205→- **Origen:** Directriz del operador: "es frustrante tener un resultado
   206→  esperado en mi mente y no obtenerlo; quiero que el LLM primero genere las
   207→  expectativas y luego compare si se obtuvo eso o algo mejor o peor".
   208→
   209→### 🟡 Regla W-CTA: Glowing CTA Button en Estados Listos
   210→**When a primary action button (Combinar, Procesar, Generar, Publicar) becomes
   211→enabled after a state condition is met (e.g., 2+ files added), it MUST use the
   212→`GlowingCtaButton` widget** with gradient + subtle pulsating glow (ver
   213→`docs/widgets/glowing-cta-button.md`).
   214→
   215→- **Estados**: disabled → enabled-glowing → hover → active → success/error.
   216→- **Glow sutil Apple-style**: expansión máxima 12-16px, opacidad 0.4, pulso 2.4s.
   217→- **`prefers-reduced-motion`**: desactiva glow, mantiene gradient.
   218→- **Verificación**: `ui test` y `persona check` validan presencia y transiciones.
   219→- **Origen:** Directriz del operador: "resalta el botón CTA de combinar con
   220→  efectos gradients glowing para instar a tocarlo cuando haya 2+ archivos".

   224→## 2. El Pipeline Universal de Desarrollo Agéntico (5 Fases Polyglot)
   225→
   226→```
   227→┌────────────────────────────────────────────────────────────────────────┐
   228→│ FASE 0: AUDITORÍA DE PREMISAS & MEMORY SYNC (Premise Audit)           │
   229→│  • Verificar afirmaciones contra el código antes de ejecutar.          │
   230→│  • Consultar docs/memory/anti-patterns.md para evitar reincidencias.   │
   231→│  • Verificar orden de arranque de infraestructura y estado de puertos. │
   232→└──────────────────────────────────┬─────────────────────────────────────┘
   233→                                   ▼
   234→┌────────────────────────────────────────────────────────────────────────┐
   235→│ FASE 1: NÚCLEO DE DATOS, DOMINIO Y TIPADO ESTRICTO                     │
   236→│  • Esquemas de datos relacionales, migraciones y modelos EAV.          │
   237→│  • Lógica pura de negocio, máquinas de estado y aislamiento de datos.   │
   238→│  • Tipado estricto (cero 'any', cero tipos dinámicos sin validar).     │
   239→│  • Emisión de eventos de dominio y registro de auditoría en mutaciones.│
   240→└──────────────────────────────────┬─────────────────────────────────────┘
   241→                                   ▼
   242→┌────────────────────────────────────────────────────────────────────────┐
   243→│ FASE 2: CONTRATOS DE INTERFAZ Y ENVOLTORIOS DE API                     │
   244→│  • Controladores y rutas con decoradores de autenticación y permisos.  │
   245→│  • Especificaciones declarativas (OpenAPI 3.1, Protobuf, Zod Schemas). │
   246→│  • Envoltorio canónico consistente: { success, data, error, meta }.    │
   247→│  • Excepciones explícitas de protocolo (nunca HTTP 200 con error body).│
   248→└──────────────────────────────────┬─────────────────────────────────────┘
   249→                                   ▼
   250→┌────────────────────────────────────────────────────────────────────────┐
   251→│ FASE 3: SUPERFICIE DE CONSUMO, UI Y COMPOSICIÓN DE WIDGETS             │
   252→│  • Widgets polimórficos EAV con Object Type (ot) e Instance (oi).      │
   253→│  • Adaptadores de consumo (transformación snake_case <-> camelCase).   │
   254→│  • 4 estados obligatorios: Loading (esqueleto), Vacío, Error y Éxito.  │
   255→│  • Accesibilidad WCAG 2.1 AA (contraste, foco por teclado, ARIA).      │
   256→└──────────────────────────────────┬─────────────────────────────────────┘
   257→                                   ▼
   258→┌────────────────────────────────────────────────────────────────────────┐
   259→│ FASE 4: TESTS, DOCUMENTACIÓN Y ACTUALIZACIÓN DE MEMORIA                │
   260→│  • Pruebas de contrato contra esquemas OpenAPI/Protobuf.               │
   261→│  • Tests unitarios y de integración para métodos de servicio.          │
   262→│  • Sincronización de documentación técnica y manuales de arquitectura. │
   263→│  • Registro de aprendizajes en docs/memory/ (WINS y Anti-Patterns).    │
   264→└──────────────────────────────────┬─────────────────────────────────────┘
   265→                                   ▼
   266→┌────────────────────────────────────────────────────────────────────────┐
   267→│ FASE 5: VALIDACIÓN EN CALIENTE Y PUERTAS DE COMPILACIÓN                │
   268→│  • Compilación completa del proyecto con cero errores y warnings.      │
   269→│  • Linter y análisis estático estricto ejecutados y registrados.       │
   270→│  • Smoke test real: invocación HTTP (curl) o inspección de navegador.  │
   271→│  • Si falla > 3 intentos consecutivos: solicitar intervención humana.  │
   272→└────────────────────────────────────────────────────────────────────────┘
   273→```

   275→### 2.1 Matriz de Adaptación Polyglot
   276→
   277→| Lenguaje / Ecosistema | Fase 1: Datos y Tipado | Fase 2: Contratos de API | Fase 4: Batería de Pruebas | Fase 5: Compilación y Puertas |
   278→| :--- | :--- | :--- | :--- | :--- |
   279→| **TypeScript / Node** | Prisma / Drizzle; tipos estrictos; `no-explicit-any`. | OpenAPI 3.1; Zod; decoradores de permisos. | Vitest / Jest; tests de contrato OpenAPI. | `pnpm exec tsc --noEmit && pnpm build && pnpm lint` |

   307→### 3.3 Formulación Matemática de Resiliencia
   308→Para evitar tormentas de reintentos (*thundering herds*) y gestionar fallos en
   309→cascada:
   310→
   311→1. **Detección de Fallos en Ventana Deslizante:**
   312→   Para un modelo $M$ dentro de una ventana con $N$ muestras ($N \ge N_{\min}$,
   313→   con $N_{\min} = 10$):
   314→
   315→   $$R_{\text{fail}} = \frac{\sum_{i=1}^{N} \mathbb{I}(e_i \in \{5xx, 429, \text{Timeout}\})}{N}$$
   316→
   317→   El interruptor conmuta al estado `OPEN` si:
   318→
   319→   $$N \ge N_{\min} \quad \land \quad R_{\text{fail}} \ge \theta_{\text{fail}} \quad (\theta_{\text{fail}} = 0.40)$$
   320→
   321→2. **Backoff Exponencial con Jitter Decorrelacionado:**
   322→   Para reintentos transitorios dentro del mismo proveedor:
   323→
   324→   $$T_{\text{sleep}} = \min\left(T_{\max}, \; \text{random}(T_{\text{base}}, \; T_{\text{prev}} \times 3)\right)$$
   325→
   326→   Donde $T_{\text{base}} = 200\text{ ms}$ y $T_{\max} = 3000\text{ ms}$.
   327→
   328→> El desarrollo formal y los pseudocódigos están en
   329→> `docs/l2-control-plane/resilience-math.md`.

   347→## 4. Gobernanza Evolutiva PRE-v2.0 y Protocolo de Medición PSIM
   348→
   349→### 4.1 Framework PSIM (Positive Self-Improvement & Measurement)
   350→
   351→PSIM establece la medición simétrica positiva del desempeño del agente: no solo
   352→registra fallos, sino que cuantifica las capacidades adquiridas.
   353→
   354→**Las 8 Clases de Victoria (W1–W8):**
   355→
   356→| ID | Nombre | Descripción |
   357→| :--- | :--- | :--- |
   358→| **W1** | Capability Strengthening | Nueva capacidad funcional o profundización de moat. |
   359→| **W2** | Carry-over Closure | Cierre de una deuda técnica postergada en rondas previas. |
   360→| **W3** | Mock Reduction | Migración de tests simulados hacia dependencias reales de integración. |
   361→| **W4** | ADOPTED Promotion | Promoción de una tecnología de evaluación a estándar del proyecto. |
   362→| **W5** | Anti-Pattern Retirement | Eliminación comprobada y sostenida de un antipatrón en el código. |
   363→| **W6** | Persona Satisfied | Cumplimiento verificado de los requerimientos de una persona de usuario. |
   364→| **W7** | Gate Velocity | Reducción cuantificable del tiempo de compilación o ejecución de tests. |
   365→| **W8** | Finding Half-Life | Resolución de un hallazgo crítico dentro de los plazos establecidos. |
   366→
   367→**Los 5 KPIs de Trayectoria:**
   368→
   369→| ID | Nombre | Objetivo |
   370→| :--- | :--- | :--- |
   371→| **K1** | P0/P1 Closure Rate | $\ge 90\%$ de hallazgos críticos cerrados. |
   372→| **K2** | Mock Reduction Velocity | Pendiente neta negativa en la cantidad de stubs artificiales. |
   373→| **K3** | Finding Half-Life | Vida media de hallazgos $\le 2$ iteraciones. |
   374→| **K4** | Capability-Strengthening Count | Al menos 1 victoria W1 por iteración. |
   375→| **K5** | Gate Stability Streak | Racha monótonamente creciente de compilaciones y pruebas limpias. |
   376→
   377→### 4.2 Gobernanza PRE-v2.0 (Perpetual Rule Evolution)
   378→
   379→Para evitar que los LLMs degraden o relajen sus propias restricciones a lo largo
   380→del tiempo, se aplica una separación estricta de 3 roles:
   381→
   382→1. **Ejecutor (Code Agent):** Escribe código siguiendo este `AGENTS.md`. Tiene
   383→   estrictamente prohibido modificar los archivos de reglas.
   384→2. **Optimizador (Rule Engineer):** Propone modificaciones a `AGENTS.md` o prompts
   385→   en ramas aisladas (`pre/propose/*`) fundamentadas en análisis de causa raíz.
   386→3. **Juez Determinista (`packages/eval`):** Software compilado sin LLM que evalúa
   387→   las propuestas contra un benchmark histórico.
   388→
   389→**Puntuación Constitucional:**
   390→
   391→$$S = 100 \times \sum_{i=1}^{6} (w_i \cdot D_i)$$
   392→
   393→Donde:
   394→- $D_1$ Compilación/Tipado ($w_1 = 0.20$)
   395→- $D_2$ Fidelidad de Contratos ($w_2 = 0.15$)
   396→- $D_3$ Adherencia al Pipeline ($w_3 = 0.20$)
   397→- $D_4$ Casos Ocultos ($w_4 = 0.20$)
   398→- $D_5$ Eficiencia de Tokens ($w_5 = 0.10$)
   399→- $D_6$ Arquitectura/Reglas Críticas ($w_6 = 0.15$)
   400→
   401→**Condición de Promoción Inviolable:**
   402→
   403→$$\Delta S \ge \epsilon \ (\epsilon = 5.0) \quad \land \quad \forall i, \ \Delta D_i \ge -\delta \ (\delta = 2.0) \quad \land \quad (\sigma_{\text{candidato}} + \sigma_{\text{base}}) < |\Delta S|$$
   404→
   405→> El detalle del juez determinista y el benchmark rotativo ciego anti-Goodhart
   406→> vive en `docs/governance/PRE-v2.0.md`.

   470→## 8. Protocolo de Sesión Agéntica
   471→
   472→### 8.1 Apertura de Sesión (Fase 0 obligatoria)
   473→1. Leer `AGENTS.md` (este archivo) en su totalidad.
   474→2. Leer `docs/memory/anti-patterns.md` para evitar reincidencias.
   475→3. Leer el último bloque de `docs/memory/worklog.md` para contexto del estado.
   476→4. **Leer los últimos 3 reportes de `docs/reports/`** (ordenados por epoch desc) para mantener continuidad de specs pendientes y no perder hallazgos previos.
   477→5. Verificar infraestructura local (DB, Redis, puertos) con `scripts/start.sh`.
   478→6. Declarar `DEV_OS` y `DEPLOY_OS` (Regla P10) antes de cualquier script.
   479→7. Declarar el alcance planificado antes de cualquier mutación.
   480→
   481→### 8.2 Durante la Sesión
   482→- Aplicar las 5 Fases del Pipeline Universal en orden estricto.
   483→- Cumplir las **15 Reglas Cardinales (P1–P15)** + Regla W-CTA en cada operación.
   484→- **ANTES de implementar cualquier feature**: generar documento de expectativas (P15) con skill `expected-spec-generator`.
   485→- Tras cada edición, ejecutar Regla P1 (Read-After-Edit).
   486→- Tras cada puerta de validación, ejecutar Regla P2 (Gate Honesty) — y la verificación DEBE ser por browser headless (P14), no curl/fetch aislado.
   487→- Tras crear una vista compleja, ejecutar Regla P11 (Onboarding Tour obligatorio).
   488→- Tras ingerir input externo, ejecutar Regla P12 (Anti-Prompt-Injection 7 capas).
   489→- Antes de publicar cualquier artefacto, ejecutar Regla P13 (Auto-crítica obligatoria).
   490→- Tras implementar, ejecutar `expected-check <topic>` (P15) para comparar resultado vs expectativa.
   491→- Si un CTA se habilita por condición cumplida, aplicar Regla W-CTA (GlowingCtaButton).
   492→- Si una tarea falla > 3 veces consecutivas: abortar y escalar a humano.
   493→
   494→### 8.3 Cierre de Sesión (Fase 5 + Reporte + Auto-Crítica)
   495→1. Ejecutar `scripts/verify.sh` y reportar Gate Honesty honesto.
   496→2. Actualizar `docs/memory/wins-ledger.md` con al menos 1 victoria PSIM.
   497→3. Si se descubrió un nuevo antipatrón, anexarlo a `anti-patterns.md`.
   498→4. Anexar el bloque de handoff al `worklog.md` con:
   499→   - Estado general, artefactos producidos, siguientes pasos.
   500→5. **Generar reporte de cierre en `docs/reports/<epoch>-<title>.md`** donde:
   501→   - `<epoch>` = segundos desde Unix epoch (`date +%s`).
   502→   - `<title>` = kebab-case descriptivo (ej. `cold-run-fix-rbac-gaps`).
   503→   - Ejemplo: `docs/reports/1759344000-cold-run-fix-rbac-gaps.md`.
   504→   - El reporte incluye: veredicto AGREE/DISAGREE por hipótesis, cambios realizados, resultados de puertas (Gate Honesty), análisis crítico contrario (¿hay mejores formas?), siguientes pasos.
   505→6. **Auto-crítica obligatoria (Regla P13)**: el reporte debe incluir:
   506→   - **Modo A** (self-revision): al menos 3 debilidades reales del trabajo hecho.
   507→   - **Modo D** (adversario, si toca seguridad/tools): 2 vectores de ataque probados.
   508→   - **Tabla AGREE/DISAGREE**: al menos 1 DISAGREE si exploró algo nuevo.
   509→   - **Análisis crítico contrario**: "¿hay mejores formas? ¿newer ways 2026?".
   510→7. El reporte es **inmutable una vez escrito** (Regla P9 extendida a `docs/reports/`); correcciones via nuevo reporte con referencia `[CORRIGE-REPORT-<epoch>]`.
