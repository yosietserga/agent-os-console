    14→## ¿Por qué existe este boilerplate?
    15→
    16→Porque estás cansado de escribir lo mismo en cada proyecto, para cada LLM, para
    17→modelar y moderar su comportamiento. Esta plantilla captura **una vez** toda la
    18→gobernanza agéntica — reglas, memoria, resiliencia, medición — y la hace reusable
    19→en cualquier repositorio, con cualquier proveedor LLM/SLM y en cualquier lenguaje.
    20→
    21→> **Filosofía:** *"Escribe las reglas una vez. Opéralas para siempre."*
    22→>
    23→> **Objetivo:** que el operador pueda decir **"clona este repo y crea una app…"**
    24→> y todo quede por sentado — sin más agotamientos, ni desgastes, ni degradaciones.

   118→## 2. Diagrama maestro del workflow de cada prompt

   121→Ilustra los 4 tipos de paths: **secuenciales** (↓), **alternos** (◇), **recíprocos**
   122→(↔) y **paralelos** (║).

   130→     │
   131→     ▼
   132→ ┌─────────────────────────────────────────────────────────────────────────────────────┐
   133→ │  PASO 1 — INGESTA DEL PROMPT                                                        │
   134→ │  El LLM/SLM recibe el prompt y detecta el patrón canónico                           │
   135→ │  "lee AGENTS.md, ejecuta: X"                                                        │
   136→ └────────────────────────────────────────────┬────────────────────────────────────────┘
   137→                                              │
   138→                                              ▼
   139→ ┌─────────────────────────────────────────────────────────────────────────────────────┐
   140→ │  PASO 2 — FASE 0 (AUDITORÍA DE PREMISAS & MEMORY SYNC)  ── PATHS PARALELOS          │

   144→ │   ║  (Documento Cero)   ║   ║  .md (AP-001..014)  ║   ║ de worklog.md      ║       ║
   145→ │   ╚═════════╤═══════════╝   ╚═════════╤═══════════╝   ╚═════════╤═══════════╝       ║
   146→ │             └──────────────┬──────────┴─────────────────────────┘                   ║
   147→ │                            ▼                                                         ║
   148→ │   ╔═══════════════════════════════════════════════════════════════╗                 ║
   149→ │   ║  Leer últimos 3 reportes de docs/reports/ (epoch desc)        ║                 ║

   239→## 3. Path secuencial — Pipeline de 5 fases
   240→
   241→El pipeline es el camino **secuencial estricto** que toda mutación al código
   242→debe seguir. Saltarse fases es un antipatrón (#64) y el juez PRE-v2.0 lo penaliza
   243→en $D_3$ (Adherencia al Pipeline).
   244→
   245→```
   246→═══════════════════════════════════════════════════════════════════════════════
   247→                              PIPELINE SECUENCIAL
   248→═══════════════════════════════════════════════════════════════════════════════
   249→
   250→  ┌─────────────────────────────────────────────────────────────────────────┐
   251→  │  FASE 0 — AUDITORÍA DE PREMISAS & MEMORY SYNC                          │
   252→  │                                                                         │
   253→  │  · Verificar afirmaciones contra el código antes de ejecutar            │
   254→  │  · Consultar docs/memory/anti-patterns.md para evitar reincidencias    │
   255→  │  · Verificar orden de arranque de infraestructura y estado de puertos  │
   256→  │  · Leer últimos 3 reportes de docs/reports/                            │
   257→  └─────────────────────────────────┬───────────────────────────────────────┘
   258→                                     │
   259→                                     ▼  (solo si F0 pasa)
   260→  ┌─────────────────────────────────────────────────────────────────────────┐
   261→  │  FASE 1 — NÚCLEO DE DATOS, DOMINIO Y TIPADO ESTRICTO                   │
   262→  │                                                                         │
   263→  │  · Esquemas relacionales, migraciones, modelos EAV                     │
   264→  │  · Lógica pura de negocio, máquinas de estado, aislamiento de datos    │
   265→  │  · Tipado estricto (cero 'any', cero tipos dinámicos sin validar)      │
   266→  │  · Emisión de eventos de dominio + registro de auditoría en mutaciones │
   267→  └─────────────────────────────────┬───────────────────────────────────────┘
   268→                                     │
   269→                                     ▼  (solo si F1 pasa)
   270→  ┌─────────────────────────────────────────────────────────────────────────┐
   271→  │  FASE 2 — CONTRATOS DE INTERFAZ Y ENVOLTORIOS DE API                   │
   272→  │                                                                         │
   273→  │  · Controladores y rutas con decoradores de auth y permisos            │
   274→  │  · Especificaciones declarativas (OpenAPI 3.1, Protobuf, Zod)          │
   275→  │  · Envoltorio canónico: { success, data, error, meta }                 │
   276→  │  · Excepciones explícitas (nunca HTTP 200 con error body)              │
   277→  └─────────────────────────────────┬───────────────────────────────────────┘
   278→                                     │
   279→                                     ▼  (solo si F2 pasa)
   280→  ┌─────────────────────────────────────────────────────────────────────────┐
   281→  │  FASE 3 — SUPERFICIE DE CONSUMO, UI Y COMPOSICIÓN DE WIDGETS           │
   282→  │                                                                         │
   283→  │  · Widgets polimórficos EAV (Object Type ot + Instance oi)             │
   284→  │  · Adaptadores snake_case ↔ camelCase                                  │
   285→  │  · 4 estados obligatorios: Loading, Vacío, Error, Éxito                │
   286→  │  · WCAG 2.1 AA (contraste, foco teclado, ARIA)                         │
   287→  │  · Layout 7 posiciones canónicas (P6) + paleta Apple (P5)              │
   288→  └─────────────────────────────────┬───────────────────────────────────────┘
   289→                                     │
   290→                                     ▼  (solo si F3 pasa)
   291→  ┌─────────────────────────────────────────────────────────────────────────┐
   292→  │  FASE 4 — TESTS, DOCUMENTACIÓN Y ACTUALIZACIÓN DE MEMORIA              │
   293→  │                                                                         │
   294→  │  · Pruebas de contrato contra esquemas OpenAPI/Protobuf                │
   295→  │  · Tests unitarios e integración para métodos de servicio              │
   296→  │  · Sincronización de documentación técnica y manuales                  │
   297→  │  · Registro de aprendizajes en docs/memory/ (WINS y Anti-Patterns)     │
   298→  └─────────────────────────────────┬───────────────────────────────────────┘
   299→                                     │
   300→                                     ▼  (solo si F4 pasa)
   301→  ┌─────────────────────────────────────────────────────────────────────────┐
   302→  │  FASE 5 — VALIDACIÓN EN CALIENTE Y PUERTAS DE COMPILACIÓN              │
   303→  │                                                                         │
   304→  │  · Compilación completa: cero errores, cero warnings                   │
   305→  │  · Linter y análisis estático estricto ejecutados y registrados        │
   306→  │  · Smoke test real: invocación HTTP (curl) o inspección de navegador   │
   307→  │  · Si falla > 3 intentos consecutivos → solicitar intervención humana  │
   308→  └─────────────────────────────────┬───────────────────────────────────────┘
   309→                                     │
   310→                                     ▼
   311→                            [CIERRE DE SESIÓN]
   312→```

   316→## 4. Paths alternos — Dispatch por comando
   317→
   318→Cada comando canónico activa un **path alterno** distinto. El dispatch es
   319→determinista: el agente no elige, rutea según el verbo del comando.
   320→
   321→```
   322→                              ┌──────────────┐
   323→                              │  PROMPT IN   │
   324→                              │ "lee AGENTS  │
   325→                              │  .md, ejecu- │
   326→                              │  ta: <cmd>"  │
   327→                              └──────┬───────┘
   328→                                     │
   329→                                     ▼
   330→                          ┌─────────────────────┐
   331→                          │  Parser canónico    │
   332→                          │  extrae <cmd>       │
   333→                          └──────────┬──────────┘
   334→                                     │
   335→       ┌─────────────────────────────┼─────────────────────────────┐
   336→       │                             │                             │
   337→       ▼                             ▼                             ▼
   338→ ╔═══════════╗               ╔═══════════╗               ╔═══════════════╗
   339→ ║  GRUPO A  ║               ║  GRUPO B  ║               ║   GRUPO C     ║
   340→ ║ bootstrap ║               ║ auditoría ║               ║ governance    ║
   341→ ║ & arranque║               ║ & verify  ║               ║ & medición    ║
   342→ ╚═════╤═════╝               ╚═════╤═════╝               ╚═══════╤═══════╝
   343→       │                           │                             │
   344→       ▼                           ▼                             ▼
   345→ ┌───────────┐               ┌───────────┐               ┌───────────────┐

   409→## 5. Paths recíprocos — Feedback loops

   411→Los paths recíprocos son **loops de retroalimentación** que mantienen al sistema

   583→## 6. Paths paralelos — Concurrencia agéntica
   584→
   585→Los paths paralelos ejecutan **múltiples operaciones simultáneamente**. Hay 4
   586→patrones de paralelismo en el sistema:
   587→
   588→### 6.1 Squad de agentes en worktrees aislados
   589→
   590→```
   591→   repo principal (main, protegido)
   592→        │
   593→        │  git worktree add
   594→        │
   595→        ├──► .worktrees/agent-A/  (rama: agent-A/task-123)
   596→        │        │
   597→        │        └──► Agent A opera aislado, sin colisiones
   598→        │
   599→        ├──► .worktrees/agent-B/  (rama: agent-B/task-456)
   600→        │        │
   601→        │        └──► Agent B opera aislado, sin colisiones
   602→        │
   603→        └──► .worktrees/agent-C/  (rama: agent-C/task-789)
   604→                 │
   605→                 └──► Agent C opera aislado, sin colisiones
   606→
   607→   merges a main se ordenan por blast radius:
   608→        bajo ──► medio ──► alto
   609→   (Best Practice #18: Límite de Blast Radius en Fusiones)
   610→```
   611→
   612→### 6.2 Servidores MCP operando en paralelo

   926→
   927→```
   928→┌─────────────────┐     ┌──────────────────┐     ┌─────────────────────┐
   929→│   EJECUTOR      │     │   OPTIMIZADOR    │     │  JUEZ DETERMINISTA  │
   930→│   (Code Agent)  │     │  (Rule Engineer) │     │   (packages/eval)   │
   931→│                 │     │                  │     │                     │
   932→│ Escribe código  │     │ Propone cambios  │     │ Software SIN LLM    │
   933→│ siguiendo       │     │ a AGENTS.md en   │     │ que evalúa contra   │
   934→│ AGENTS.md.      │     │ rama pre/propose │     │ benchmark histórico │
   935→│                 │     │                  │     │                     │
   936→│ ❌ NO puede     │     │ ❌ NO puede      │     │ ✅ Decisión         │
   937→│    tocar reglas │     │    mergear       │     │    matemática       │
   938→└─────────────────┘     └──────────────────┘     └─────────────────────┘
   939→```
   940→
   941→**Condición de promoción inviolable:**
   942→
   943→$$\Delta S \ge 5.0 \quad \land \quad \forall i, \Delta D_i \ge -2.0 \quad \land \quad (\sigma_c + \sigma_b) < |\Delta S|$$
   944→
   945→- $\Delta S$ — mejora de puntuación total (sobre 100)
   946→- $\Delta D_i$ — cambio por dimensión (6 dimensiones: compilación, contratos, pipeline, casos ocultos, tokens, arquitectura)
   947→- $\sigma$ — desviación estándar (significancia estadística anti-suerte)
   948→

   982→## 13. Control Plane L2
   983→
   984→### Estado del Circuit Breaker (máquina finita)
   985→
   986→```
   987→                         failure_rate ≥ 0.40
   988→                         (N ≥ 10 muestras)
   989→   ┌──────────┐  ─────────────────────────────►  ┌──────────┐
   990→   │  CLOSED  │                                  │   OPEN   │
   991→   │ (normal) │  ◄─────────────────────────────  │(bloqueado)│
   992→   └──────────┘   canary OK tras T_reset         └─────┬────┘
   993→        ▲                                             │
   994→        │                                             │ tras T_reset_ms
   995→        │                                             ▼
   996→        │                                        ┌───────────┐
   997→        └──────────  canary OK  ─────────────────│ HALF_OPEN │
   998→                                           │     └───────────┘
   999→                                           │ canary FAIL
  1000→                                           ▼
  1001→                                      ┌──────────┐
  1002→                                      │   OPEN   │
  1003→                                      │ (reset)  │
  1004→                                      └──────────┘
  1005→```
  1006→
  1007→### Backoff exponencial con jitter decorrelacionado
  1008→
  1009→$$T_{\text{sleep}}^{(k)} = \min\left(T_{\max}, \; \text{random}(T_{\text{base}}, \; T_{\text{prev}} \times 3)\right)$$
  1010→
  1011→- $T_{\text{base}} = 200$ ms · $T_{\max} = 3000$ ms
  1012→- Solo reintentos transitorios (429, 5xx, timeout). Nunca 400/401/403/422.
  1013→

  1015→
  1016→| Arquetipo | SLA | Primario | Fallback | Escalado |
  1017→| :--- | :---: | :--- | :--- | :--- |

  1019→| Accounting-OCR | 4000ms | DeepSeek V3.2 | GPT-4.1 mini | Upgrade → DeepSeek R2 |
